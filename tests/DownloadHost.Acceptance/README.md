# Local Windows Download Manager acceptance fixture

This separate test executable runs the production WPF window, WebView2 UI,
downloads bridge, coordinator, HTTP engine and DPAPI/SQLite store. A loopback HTTP
server supplies generated bytes. It never uses the production queue or WebView
profile. Test controls are not compiled into the production app or exposed through
its bridge. All compilation must run on this workspace's Windows computer.

Build from repository root with the existing .NET SDK:

```powershell
$env:DOTNET_ROOT = Join-Path (Get-Location) 'artifacts\dotnet'
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) 'artifacts\dotnet-home'
& "$env:DOTNET_ROOT\dotnet.exe" build tests/DownloadHost.Acceptance/DownloadHost.Acceptance.csproj -c Release --no-restore
$fixtureRoot = Join-Path (Get-Location) 'artifacts\downloads-32-6b-acceptance-example'
& '.\tests\DownloadHost.Acceptance\bin\Release\net8.0-windows10.0.19041.0\DownloadHost.Acceptance.exe' $fixtureRoot
```

Use a new immediate child of repository `artifacts/` whose name starts with
`downloads-32-6b-acceptance-`. An existing folder must have the fixture-owned
marker. The fixture keeps its HTTP port across restarts and stores only generated
outputs. Open Downloads & Transfers, then its Download Manager card. All actions
in that page operate through the real native adapter.

Write one of these exact values to `control.txt` in the fixture root to prepare a
scenario (ordinary filesystem editing; never a terminal command inside the UI):

| Value | Effect |
|---|---|
| `seed` | Seven held jobs: two slow, unknown size, unsafe validator, changed entity, initial 404/retry, fast completion |
| `large` | 250 held jobs, one with a 240-character filename |
| `disk` | Inject zero available space and enqueue a real HTTP job; this does not fill the drive |
| `space` | Restore the real drive free-space query |
| `changed` | Change the generated resource ETag from v1 to v2 |
| `retry-ready` | Change the initial retry endpoint from 404 to successful content |
| `idle` | No action; use before closing/reopening to avoid repeating a seed command |

The timer processes command changes, not each tick. Before restart set `idle`;
the last command is not persisted as already consumed. Do not repeat `seed` or
`large` in the same fixture and expect duplicate filenames to be admitted.
Use UI Start/Pause/Resume/Cancel/Retry/Open folder for actual acceptance. Remove
forgets metadata and retains files; confirm the intended generated test record
before exercising it. File cleanup is intentionally not automatic.

`endpoint.txt` contains the loopback base URL. Add `fast` or `slow` to that base
when testing the real new-download dialog, and select the fixture `output/`
folder with the native picker. Generated bytes are the absolute index modulo 251;
fast outputs are 1 MiB and slow outputs 64 MiB. `requests.jsonl` records only
endpoint mode, method, range offset and fixture ETag, never full request URLs.
`snapshot.json` contains redacted native views and actual WPF DPI. The server and
timer stop when the window closes. Retained files/queue allow restart validation.

The initial window width is the production host's minimum 1180 DIP, allowing the
narrow list and modal layout to be inspected without changing production shell
dimensions. The fixture cannot substitute for real Windows display scaling or a
spoken screen-reader test. See [recorded results](../../docs/downloads-slice-32-6b.md).
