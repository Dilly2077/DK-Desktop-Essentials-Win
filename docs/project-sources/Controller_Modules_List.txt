I recommend separating development into **backend implementation, UI integration, and real-world testing**, rather than treating a module as finished as soon as its code compiles.

That also gives us a way to distribute work between Chat and Codex without using Codex for tasks that Chat can handle adequately.

I've based this roadmap on your original **31-module master index**, the controller audit documents, and the current GitHub repository.

My recommendation is to **leave Module 1's UI until Module 2's backend is complete**. Both modules use the same controller information, so we can create a unified interface instead of building the UI twice.

There is one exception: run an early physical-controller discovery check before building Module 2, to establish that the existing input provider works on your PC.

### What remains after all six slices?

At that point, Module 2 should have a testable backend. It will still need the diagnostic UI, including live controller diagrams, drift graphs, calibration controls, timing charts and report export screens.

We will also need physical tests using controllers with known behaviour. A synthetic drift sample can prove the maths, but it cannot establish that the app identifies drift accurately on every controller or driver.

The UI can then be developed alongside Module 1's UI.

For Module 2, this gives us two primarily Chat-sized slices, three primarily Codex-sized slices and one that deliberately moves between both. That avoids assigning all six slices to separate heavy Codex development sessions.

An important distinction: Chat can edit GitHub code and inspect CI results, but cannot substitute for Windows hardware testing. Also, this is a workload strategy, not a guaranteed calculation of subscription usage.

The strongest candidates for completing substantial backend work entirely in Chat are **Driver Confidence Ranking, Subtitle Tools, Image Toolkit and parts of the PDF Toolkit**. System Information Export is another reasonable candidate once the Windows data-collection interface is defined.

Even these will require final UI integration and release tests. They should not be called finished user-facing modules until those steps are complete.

### Dependencies worth planning around

To avoid rebuilding shared components, we should keep several dependencies in mind:

- Modules 1–4 reuse the controller input and profile infrastructure.
- Modules 7–11 should share hardware telemetry rather than independently poll the same sensors.
- Modules 13–15 should share hardware identification, provenance and diagnostic-report models.
- Modules 18–20 and 30 should share a secure LAN pairing and authentication foundation.
- Modules 23 and 28 can share an OCR pipeline.
- Module 29's Macro Engine should expose an action interface usable by Modules 1, 4, 20 and 30.

These are implementation recommendations; the original audit describes related capabilities but does not prescribe these exact development stages.

## 6. A completion report after every slice

I recommend requiring the same completion report from both Chat and Codex. This should also go into the repository documentation, so another development session can pick up without reconstructing the history.

| Status field | What must be recorded |
|---|---|
| Implemented | Exact features and files changed |
| GitHub | Branch, PR, merged commit |
| Automated tests | Passed, failed or not run |
| Remaining backend | Outstanding functionality and future slices |
| UI | Complete, partial or not started |
| Real-world testing | Hardware/device/manual acceptance status |
| Known limitations | Compatibility, driver, privacy and safety restrictions |
| Next action | Specific next slice and whether Chat or Codex should handle it |

No slice should receive a final **Complete** status simply because code was committed. We should distinguish *implemented*, *CI verified*, *hardware verified* and *release ready*.
